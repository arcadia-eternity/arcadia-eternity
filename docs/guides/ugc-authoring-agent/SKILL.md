# Arcadia content authoring

## Choose a project

For new species, skills, marks or effects, run `arcadia-content init pack <directory>`. For a tournament format or a combination of existing packages, run `arcadia-content init environment <directory>`. Use a new or empty directory. When editing an existing project, inspect its `package.json` and run `arcadia-content workspace <directory> describe`. A content pack declares `arcadia`. A standalone environment declares `arcadiaEnvironment` and lists its content packages in npm `dependencies`.

## Debug a standalone environment

1. Read the environment with `environment_list` and its schema with `author_reference` topic `environment`. Keep the current ID and package selections when changing a rule. Pass the returned version as `expectedVersion` to `environment_save`. The rule declaration, capability requirements and package versions together determine what to test.
2. Save test teams with `team_save` or edit `debug/teams/*.yaml`. Use species and skills from the declared packages. For a ban, prepare two legal teams and a third that violates just the proposed restriction.
3. Start `arcadia-content workspace <directory> preview --execute` or connect `arcadia-content-mcp <directory> --execute` and call `preview_start`. The environment project itself supplies the rules and members. Poll `job_get` on MCP until the preview succeeds. Call `team_validate` with that preview’s `jobId` and each saved `teamId`. Check `valid` and record the diagnostic for the intended violation. Then use `battle_create` with the two legal team IDs and a fixed seed.
4. Prepare a fresh preview after changing rules or dependencies. Record the tested environment ID, revision, teams, seed and observed result. Stop the preview with Ctrl+C or `job_cancel`. When an installable archive is requested, run `arcadia-content workspace <directory> pack --execute` or call `package_build`. In the desktop environment library, choose **安装环境包** to install the resulting .tgz or an exact npm version. Local play switches when the user chooses **本地使用**. See the [CLI and MCP workflows](references/tool-workflows.md) for event inspection and conflict handling.

## Author a content pack

Work in the author's content project. Ask for the desired game behavior when its trigger, target or lifetime is ambiguous. Use the SDK and host version available to the project. `arcadia.sdkApi` identifies the compatible SDK API.

1. Read `package.json` and the actual source layout: `data/species`, `data/skills`, `data/marks`, `src`, `assets`, `locales`, `test` and `arcadia.config.mjs`. Some older projects still use a root `content.json`; follow their manifest rather than assuming it. Do not edit generated `dist` as source. If the host repository is available, consult `docs/guides/npm-content.md` and `docs/guides/effect-sdk.md`. Do not assume SDK packages have been published merely because a version is in a manifest.
2. Declare behavior with `@effect` and `@on` in `src/effects/*.effect.ts`; for parameters or bindings use a decorated class with `static create(context)` returning `defineCodeEffect`. The SDK discovers files and builds `effectArtifact`. Use canonical prototypes from the current context. Keep `projectId`, namespace, use IDs and binding keys stable unless a breaking identity change is intended. Cross-package data references require npm dependencies.
3. Implement parameters with `numberParam`, `booleanParam` or `stringParam` when battle effects must read or modify them. Use the declared source scope and capture/follow semantics; do not require a parameter editing form. Keep per-battle state in engine instances, parameters and bindings rather than module-global mutable variables. Use the battle RNG instead of `Math.random()` for battle decisions.
4. Build and run the project's own scenario tests against the real engine. For a slow effect cover hit, miss, repeated application, removal and natural expiry; exercise supported waiting-point snapshot restoration if relevant. Preserve meaningful existing assertions and run independent host contract tests when available. The starter's `npm test` covers hit, miss, refresh, removal, natural expiry and restoration at a supported selection waiting point. Fix implementation failures rather than weakening unrelated tests.
5. Pack with `npm run pack` / `arcadia-content pack`, inspect the actual artifact and validate it in a separate npm installation. The author tool stages `arcadia.effectArtifact` and a closed effect module before its internal `npm pack --ignore-scripts`; plain npm pack does not generate this prebuilt artifact. Validate distributed code packages with prebuilt-only preparation so consumers need no author compilation or development dependencies. Installing, code admission and selecting a server environment are separate steps. Use the local development approval profile only for an explicitly approved local environment. Never treat a content hash, package install or client acknowledgement as permission to run code.
6. Run `check_start` and `test_start`, poll `job_get`, and fix reported file/line diagnostics with version-checked writes. Then use `preview_start` for a captured npm candidate and the full battle client. Poll `job_get` for `result.preview.url` or `clientPath`; desktop users can open that same task from the workbench. Compare the task's source revision and candidate identity with the tested revision. `demo` remains the headless demonstration. Use `job_cancel` to stop the preview from any entry point; interrupted tasks need a new run. Keep active matches on their existing candidate. The browser consumes public metadata, on-demand resources and battle messages; effects execute in the local Node host.

For CLI/MCP operations, file conflicts and desktop project locations, read [tool workflows](references/tool-workflows.md). For media, locale and cross-package references, read [project sources](references/project-sources.md). The content library supports independent species, skills and marks; ability and emblem are mark tags. Authors can create objects, pick existing references, edit scoped multilingual names/descriptions, import media and preview bindings. Creation and field edits enter drafts and require reviewed saving. Drafts survive object navigation; shared YAML fields stay read-only in forms. Use external tools for TypeScript, file organization and intentional shared-definition edits.

When connected through the desktop MCP configuration, call `workspace_context` to understand the current package, view, focused object/resource, locale, unsaved drafts and conflicts. No explicit object selection is required. Focus is context, not an edit scope or authorization; follow the user's task and use `content_query` to discover related objects as needed. `focus.visible` distinguishes the visible object from the last focused object while another tool page is open. Draft values are unsaved; do not mistake their `expectedVersion` for a revision containing those values. Read disk sources before writing, preserve unrelated user changes and leave conflicting drafts for desktop reconciliation. If context is disconnected, expired or from another project, use source inspection and conversation rather than treating old UI state as current. Do not invent a skill-to-mark field: effects connect those through actual behavior definitions and parameters.

Report the behavior changed, tests actually run, build/environment identity when available and any unmet validation. Publishing, registry credentials and deployment remain under the author's control; do not publish or deploy as a side effect of testing.

资源采用分离定义：规则位于 data/species、skills、marks；data/presentations 通过 target.kind/id 关联对象，用途字段引用稳定资源 ID；data/resources 定义 id/kind/source。不要把 presentation、assetRef/iconRef/sfxRef 写入规则。移动素材只改 source；表现、资源和语言同样需要版本检查、草稿保护及锚点保护。content_query 的 presentations/resources 可直接查询这些记录。
