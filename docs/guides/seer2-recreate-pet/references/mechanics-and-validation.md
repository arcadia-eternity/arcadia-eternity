# 机制考据与验证

## 原表没有说明时

以任务提供的资料确认身份、关联和字段语义；技能/效果数值按用户指定版本取值。机制缺失时，搜索精灵名、技能名或印记名加具体疑问（如回血比例、换场、持续回合、固定伤害），查阅社区攻略、论坛实测和对战录像。4399 等攻略可作为入口，搜索摘要只用于定位，结论应来自实际读到的页面或录像。不要因为 buff 描述为空就停止实现，也不要拿社区种族值替换已确认的 HP 不变、其余五项 +50 公式。

只记录影响实现的证据：

| 类型               | 记录方式                                                                       |
| ------------------ | ------------------------------------------------------------------------------ |
| 任务输入           | 资料标识、字段与版本，区分配置和描述文字；不在公开报告暴露未授权的来源定位信息 |
| 社区直接说明或实测 | 页面标题和 URL、发布日期/适用版本（可得时）、相关短摘录或录像时间点            |
| 社区推断           | 出处、推导过程及未排除的解释，不写成原表事实                                   |
| 项目约定           | 当前实现位置及采用理由，不称原作设定                                           |
| 尚未确认           | 具体缺失条件、影响哪个行为、已查线索                                           |

优先采用条件清楚、版本吻合且可复核的实测；多个转载不视为多个独立证据。若社区描述与客户端冲突，先排查版本、形态和描述省略，不固定认定某一方必然正确。按以下用户确认的口径作出实现选择，不因来源冲突就一律退回旧表或暂停：

- 机制解释可采用社区说明；具体技能/效果数值以用户指定版本为准。明确的数值差异不属于待修错误，记录版本与采用值即可。种族值沿用主文固定换算公式。
- 指定版本新增文字可能记录了后续实测发现的原有附加效果。先区分旧表省略、后来查明、明确改版三种情况；仅有描述差异不能证明是指定版本原创或加强。明确且自洽的补充按当前采用口径实现，查不到原始测试也不自动丢弃，但如实标明证据层级。
- 对照时逐项列出主效果与副效果、概率、目标、幅度和触发条件，给每项标注复用或新增实现，防止只比较基础数值而漏掉副效果。例如卡顿嘟嘟的红心射线 10% 降速、群心满天 10% 加物攻，旧表未写不能成为省略理由；此例不表示其他技能自动具备同样副效果。
- 指定版本描述出现极端倍率、范围、时长或前后矛盾时，检查是否可能是测试改写；结合其他说明、对应配置与可得实测判断。数值大本身不证明错误，不自行编造上限，也不一概抛弃指定版本数据。
- 存在多个有依据且可成立的机制解释时，通常选择综合技能强度最高的自洽方案；综合考虑收益、触发条件、概率、消耗、持续与联动，不能只取每个字段的最大数拼成新技能。若强弱随场景变化，说明采用判断即可；确实无法据此作出合理选择时才集中询问。
- 用一句话或小表记录“输入资料/社区/指定版本说法 → 采用数值与机制 → 理由”。这种取舍标为用户授权的实现选择，不伪称原作已证实。复用公共技能时也核对它是否符合选定口径；语义不同则独立定义，避免改坏其他精灵。

测试应证明所选方案及关键边界，不能仅因与旧表逐字段不一致就判失败，也不能用占位效果宣称完成。

## 伤害交互的范围

先分清技能物理/特殊伤害、固定或比例伤害、持续伤害、直接扣血，再检查当前引擎如何表示它们。原作类别与项目 `Effect` 枚举不是天然一一对应；应根据产生伤害的代码和具体效果确认，不能只按技能文本归类。

用户明确指出原作与 Effect 类伤害交互的机制不多。对减伤、护盾、免伤、吸血、反伤、受击触发等，逐项确定其适用来源；“受到伤害”“所有伤害”这样的简写不足以证明覆盖所有引擎路径。既不要默认全覆盖，也不要默认全部排除。

只有“该精灵在原作确实需要此交互”的证据与“当前执行路径不支持”的代码证据同时成立，才把它列为实现缺口，并选择最小适配。缺少原作证据时记录范围未确认，不为此扩展通用伤害管线。测试覆盖已证实的交互及有依据的排除项；测试通过只能证明实现符合所选规则，不能替代原作考据。

## 从机制到验证

- 为新机制挑出会改变结果的触发条件、目标、数值、持续/清除时机和换场行为；从证据写预期，不照抄实现生成断言。随机效果用固定输入，持久状态验证快照恢复。复用成熟机制时避免逐技能重复同一套测试。
- 分数阈值按原始数学条件比较：例如“低于最大生命的 1/8”可比较 `hp * 8 < maxHp`，不要先向下取整阈值。用不能整除的最大生命验证边界。
- 检查待机精灵的印记持续时间是否暂停、切换是否清除等当前运行规则，再与原作证据比较；不能将项目现状自动当成原作规则。特性/纹章仍按 skill 主文约定在战斗开始时给每只精灵创建。
- 修改 authored 效果或数据后，先重建对应内容包，再运行消费 dist 的测试；数据字段比对、战斗机制测试、客户端表现验收分别报告，不能互相代替。
- 仅在用户要求客户端验收时，优先复用当前仓库本地战斗的端到端测试助手，在独立浏览器上下文准备队伍，检查实际技能结算和战斗记录。避免修改用户正在使用的队伍存储。
- 精灵战斗 SWF、技能特效、音效分别核验。原表有 EffectID 不表示当前配置已经绑定技能动画；静态截图也不能证明动画完整或音频可播放。交付时只声称实际观察到的结果。

## 推定结算时机

“消耗印记获得先制/威力”不自动意味着命中后才消耗。先制收益在命中前已取得，应分别说明增益生效、移除印记、命中与行动取消的时点，以及提前失去防御效果的后果。接受的实现取舍与原作实测事实分开记录；不能只因 MISS 返还更强就自动采用返还。
