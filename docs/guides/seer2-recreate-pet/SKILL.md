# 赛尔号2精灵复刻

默认目标是当前作者内容项目；先读当前 AGENTS.md 和 package.json，确认安装的 SDK。只查资料时不修改内容包；要求复刻时完成数据、效果、表现和针对性验证。本 skill 随 content-dev SDK 模板分发，也可从仓库文档目录读取。

## 输入与采用口径

使用用户为当前任务提供的精灵资料、数值和素材；资料不随 skill 分发，不预设下载站点、备份仓库或本机位置。资料不足时先完成可确认部分，再集中说明影响玩法的缺口。

项目种族值换算：HP 保持输入原值；物攻、物防、特攻、特防、速度各加50。若输入使用 Atk/Def/SpAtk/SpDef/Spd，分别映射 atk/def/spa/spd/spe；特别注意输入 Spd 是速度，项目 spd 是特防。仅对未换算的值使用公式，不二次加50；已有精灵不在无关任务中批量改值。

机制可查询社区说明，具体数值按用户指定的版本。逐技能核对主效果和附加效果，不能只抄威力、命中、怒气。后来补充的描述可能来自实测，早期描述省略不等于机制不存在；未取得实测记录时注明证据层级。

异常、冲突或极端描述应结合机制判断，不机械照搬。多个有依据且自洽的候选通常采用综合技能强度最高的方案；不得叠加互不兼容的效果或凭空抬高数值。该选择不是原作事实证明。细则见 [机制考据与验证](references/mechanics-and-validation.md)。

## 快速调查

1. 用中文名、别名和图鉴编号查当前包 locales、species、skills，建立原版编号 → 当前内容 ID 对照。区分进化阶段、皮肤、形态和活动版本。系统精灵（包括系统/BOSS 专用数据）不在复刻范围内；过高编号是排查线索，结合同名记录、图鉴、获取途径和用途确认，不设未经证实的统一编号阈值。只接入玩家可获得的正常形态。默认沿 EvolvesFrom 回溯并补齐点名形态的完整正常玩家前置进化链，逐形态接入种族值、各自学习列表、特性/纹章、文本、资源和进化关系；不能只继承前置技能却漏掉前置精灵。仅在用户明确限定单一形态时缩小范围。分支、皮肤与系统形态不自动纳入。
2. `rg --files` 按目录与扩展名筛选，先查 XML/JSON/AS 文本，再查 SWF。搜索编号时用边界或结构化字段，避免把 1 匹配为 1001。保留原始字段名和值，先确认属性枚举、倍率和单位再转换。
3. 跟踪配置消费代码，确认字段语义及资源 URL 拼接规则。客户端描述只能证明文本，不自动证明服务端伤害公式、概率、触发顺序或隐藏条件。
4. 为目标整理小型证据表：种族/技能/特性/纹章、原始 ID、源文件及字段或代码位置、目标 ID、已确认行为、待核实项。记录本地源文件哈希或远端 SHA。冲突资料并列注明版本，不能默默混用。

## 接入当前引擎

实施前阅读 [当前项目的内容约定](references/project-conventions.md)，复用已核实的表示方式，并区分项目适配与原作机制。

### 独立 SDK 内容包（默认）

不要求主仓库存在。读取项目 manifest、安装的 SDK 参考与邻近示例，以 `data/species`、`data/skills`、`data/marks`、`src/effects.ts`、`locales`、`data/presentations`、`data/resources` 和 `test/*.test.mjs` 组织。进化链共享种族文件，效果按精灵或机制分组；以实际 manifest 为准，不凭空创建 base 专用注册文件。

使用 `createEffects({ sdk, marks, id })`、`sdk.defineCodeEffect` 与 SDK 的 `defineEffect`；通过项目 namespace 和显式引用连接数据。复用外部技能、印记或资源须声明运行时 dependencies，开发工具放 devDependencies。不得修改安装的不可变包、node_modules，或为实验重写加载器。

测试使用 `@arcadia-eternity/content-sdk/testing` 的 `prepareContentPack` 和标准依赖装配，不限制只能依赖 base。打包使用 `arcadia-content pack` 或项目对应脚本，检查生成预编译效果工件；在独立安装目录通过标准 `prebuilt-only` 准备验证分发产物。安装与执行准入分开，不能因为装包成功就推定允许执行。

有 MCP 时先查询工作区与 `author_reference`，版本检查后使用 `source_apply`/`content_apply` 保存，运行 `check_start`、`test_start`、`package_build`，轮询 `job_get` 并增量读取 `job_output`。仅 CLI 时用项目脚本完成同等检查。遇到 SDK 缺口，记录最小复现与阻塞，继续独立内容工作；不要自行扩展为 SDK、前端或宿主修复任务。

### 主仓库 base（仅在任务指定时）

先查看 `packs/base/pack.json`、`packs/base/content-groups.yaml`、当前格式文档和相近精灵。种族与专属效果单独存放，技能、印记、翻译和资源按现有公共表组织：

| 内容       | 默认位置（相对 `packs/base/`）                                               | 职责                                                                     |
| ---------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 种族       | `data/groups/<group>/species.*.yaml`                                         | 种族值、学习列表、特性与纹章引用；沿用当前文件编号约定，不照抄实验的序号 |
| 技能       | `data/skill.yaml`                                                            | 分类、威力、命中、怒气、目标与效果 ID                                    |
| 印记       | `data/mark.yaml`、`mark_ability.yaml`、`mark_emblem.yaml`                    | 状态、特性、纹章定义及持续、叠加、换场规则                               |
| 专属效果   | `src/effects/<pet-or-group>.ts`                                              | 集中维护该精灵或分组的原生 TypeScript 效果                               |
| 文本       | `locales/zh-CN/` 下对应的 species、skill、mark、mark_ability、mark_emblem 表 | 名称和描述                                                               |
| 表现与资源 | `data/presentations/main.yaml`、`data/resources/main.yaml`                   | 表现绑定与资源地址；核实当前 manifest，玩法记录不写资源路径              |
| 专项测试   | 仓库 `packages/battle/test/engine/<pet-or-group>.test.ts`                    | 该精灵的新机制及关键联动                                                 |

同名且同机制的技能、印记和公共效果优先复用，保持稳定 ID；语义不同再建立独立定义。专属效果遵循 `defineEffect` 的 triggers/apply 和 SDK 契约，优先参照已验证的 authored 效果；不要为集中到一个文件而复制公共机制。修改生成文件前追查生成来源，不恢复 DSL、Rule Graph 或 V2 实现。

修改主仓库 base 时检查两条注册链（独立包使用自己的 manifest/SDK 注册方式）：

- 数据：种族文件加入 `pack.json`，分组加入 `content-groups.yaml`；只有本次确实实现的进化关系才登记。
- 效果：专属文件可导出 `create<Pet>Effects(marks)`，在 `src/effects/candidate-catalog.ts` 汇入当前效果目录；按现有导出约定更新 `effects.ts`。技能和印记通过效果 ID 引用实现，仅导出函数不等于完成注册。

这套结构中，一只精灵的完整实现会跨多个文件，不能只复制种族 YAML 和效果 TS 就视为迁移完成。交付时简要列出新增文件、追加到公共表的定义及注册入口；不要新增写死精灵、技能、印记或效果总数的校验；验证引用完整性、加载一致性和实际行为。文件数量不是目标，不为单只精灵另建一套目录结构。精灵展示沿用现有 icon、portrait、battle（`seer2-swf`、source、fallback）、cry 结构。

本系统中，特性和纹章都建模为战斗开始时每只精灵自带的印记。复刻时将它们映射到 mark 定义及对应效果，并通过种族的 ability/emblem 引用及队伍装备接入现有战斗初始化流程；不是只有首发精灵才拥有，也不要改成首次上场才创建。印记已存在与效果何时触发是两回事：具体效果仍遵守原作的触发条件。先核对现有初始化实现：特性可由种族补齐，纹章需要队伍显式装备。测试首发和后备成员，不重复添加印记或另建运行机制。

逐个确认技能威力、怒气、命中、优先级、目标、次数、概率，以及特性/纹章的条件、持续时间、叠层、清除、换场和结算时机。原表未说明的机制，主动搜索社区攻略、实测与对战录像补全；阅读 [机制考据与验证](references/mechanics-and-validation.md)，区分社区直接说明、推断和项目约定。有适用且可信的社区依据即可继续实现，并保留出处；仅对查证后仍影响玩法的关键歧义集中询问用户，继续完成不受影响的部分。

原作能与 Effect 类伤害交互的机制较少，这是逐项核实的背景，不代表一律不交互。不要仅凭“所有伤害”“减伤”等描述就把效果扩展到 Effect 伤害，也不要仅因当前引擎的 Effect 路径绕过某钩子便判定引擎缺陷。只有原作代码、社区实测等证据支持具体交互时才接入并验证；未证实的交互保持未确认，不擅自扩大范围。

使用引擎提供的随机数和状态 API，保持确定性和快照恢复；跨触发状态不放模块变量或闭包。不要为单只精灵引入未经需要的引擎重构。

资源按已确认编号与加载规则逐项匹配，不能凭文件名就认定同一形态。优先复用已有导出图和 SWF 播放链；需要转换时保留透明度、帧、尺寸和朝向。遵循项目资源按需加载与 HTTP(S) 直连约定，不新增预取或共享缓存。只复制实际所需资源到用户指定的可编辑包，不改已安装的不可变包，也不把本机绝对路径写进可分发配置。

## 验证与交付

编写或修改测试前阅读 [测试组织与写法](references/testing.md)。独立内容包使用 `test/*.test.mjs` 和包自身脚本；主仓库 base 使用 `packages/battle/test/engine/<group>.test.ts`，并执行专用类型与 lint 检查。同进化链复用同一测试文件；实验材料留在指定临时目录，不混入正式测试或分发包。

- 检查 manifest/分组注册、所有技能/印记/效果/翻译/资源引用、ID 唯一性和资源实际存在。
- 修改内容包后先按当前 package scripts 重建该包，再运行读取其 dist 的战斗测试，避免测到旧效果。base 包可核实并使用 `pnpm --filter @arcadia-eternity/data-pack-base build`。依赖产物过期时按 AGENTS.md 先 frozen install 和相关依赖构建，再判断类型错误。
- 新机制用固定随机输入验证关键触发、边界、持续与换场；持久状态涉及快照时验证恢复前后一致性。已有机制复用不机械增加重复测试。
- 默认实验验证内容数据、效果、构建/类型及战斗测试；客户端试玩与 Web UI 测试仅在用户要求时执行，不让前端排错阻塞内容实验。未运行的视觉/音频验收如实标明。
- 交付简短说明：已复刻形态、数据来源、复用/新增机制、验证结果及尚缺原作证据。资料不足也交付已确认数据和具体缺口，不编造“完整还原”。除非用户要求，不提交、推送或发布。
