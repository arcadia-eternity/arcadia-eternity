# 内容包管理：信息结构与布局

日期：2026-10-29。已选择“列表与侧栏”布局。本文替代上一版以服务器项目／“环境”为主对象的界面设计。包级管理已接入本地 IPC、实际 npm 安装与本机服务；当前落地范围见 [内容包管理](./content-management.md)，不以交互草图作为功能验收。

## 已确定的范围

- 采用第一种布局：左侧任务导航、中间内容包列表、右侧所选包详情；移动端变为列表与详情的层级导航。
- **网页端只读**：可以查看当前房间提供的内容包、版本、依赖、展示内容和队伍引用。搜索、筛选、展开详情属于本地查看交互，不修改内容。
- **只有本地端可以修改**：安装、启停、更新、卸载、创作内容编辑，以及本机运行管理都通过本地宿主能力完成。网页端隐藏这些入口，不提供远程代操作。
- **暂不做开放服务**：不建设公共工坊／目录、上传发布服务或远程内容管理接口，不新增浏览器可调用的内容写入 HTTP／WebSocket API。已有对战所需的公开内容读取继续复用。
- 只读边界针对 UGC 内容包和创作管理，不扩大成“网页不能编辑队伍或正常对战”。

## 参考与取舍

- [r2modman 官方仓库](https://github.com/ebkr/r2modmanPlus)：已安装列表是管理主体；获取内容与已安装内容分开，配置编辑、设置另有入口。参考其列表、按包操作与详情展开，不沿用强制先选 profile 的启动流程。仓库内截图是示意参考，不作为最新版本界面承诺。
- [Prism Launcher 的 Mods 页面](https://prismlauncher.org/wiki/help-pages/loader-mods/)：优先呈现包名称、版本与启用状态，添加文件、更新、移除围绕所选包操作。参考紧凑列表和直接的启停；不向玩家暴露目录树或普通运行库。
- [Factorio 的 Mod GUI 设计](https://factorio.com/blog/post/fff-272)：管理、安装、更新按任务分组；版本差异、更新日志可以检查。[后续改进](https://factorio.com/blog/post/fff-391)进一步把缺依赖、版本不符和冲突明确呈现，并让用户能直接进入管理器解决问题。

Arcadia 的战斗由宿主执行。桌面本机宿主能够安装内容包；连接远程服务器的普通玩家读取公开内容，不需要安装或执行服务器的效果代码。不能照搬客户端启停就改变联机规则的交互。

## 用户要管理的对象

主对象是**内容包**：名称、作者、版本、来源、提供的内容、依赖、安装状态，以及是否供本机新对局使用。

“已安装”和“已启用”分开：停用保留包及队伍配置，卸载才移除本机安装；仍被活动对局或保留引用使用的实例由宿主延后回收。普通 JS 依赖折叠在包详情中，由依赖管理器处理，不与精灵／技能内容包并列。

固定组合、锁文件、服务器环境 ID 和私有项目目录继续存在于宿主内部。默认有一套本机选择，玩家无需创建或命名“环境”。以后若确实需要保存多套组合，再提供可选的“保存为方案”，不作为首次使用前提。

## 导航结构

顶层按任务收口：

- **对战**：匹配、房间、人机／本机试战、战报。
- **队伍**：队伍编辑与精灵仓库。
- **图鉴**：查看精灵、技能、印记。
- **内容包**：安装与管理可用内容。
- **创作**：创作项目、精灵／技能／印记／TypeScript 效果编辑、测试与导出。
- **设置**：连接与偏好；“本机服务”属于其中的高级功能。

这是信息归属，不要求一次重写全部既有页面。先调整 UGC 区域与入口，既有对战、队伍和图鉴内容按原实现复用。

创作和使用内容是不同任务，保留独立入口。玩家的包详情可以展示来源与作者，但不会变成编辑表单。服务进程、监听地址、项目目录登记、服务器项目导出／恢复移到“设置 → 本机服务 → 高级项目管理”。

## 内容包页

默认进入桌面本机的“已安装”。页面明确标识“用于本机建房和试战”，不通过一个含义模糊的“环境”下拉选择作用域。

选定桌面布局：左侧窄任务栏＋中间包列表＋右侧所选包详情。网页端沿用同一结构，列表显示服务器／房间实际提供的内容，详情只读，主操作不出现安装或启停。

- 任务栏：已安装、已启用、需处理；独立分组提供“房间内容”。设置不重复出现在主列表工具栏。
- 列表顶部：搜索当前列表、添加内容包；没有常驻的安装／准入／启动／导出按钮墙。
- 列表行：小图标、名称、作者／一句描述、已装版本、状态、启停。官方基础内容置顶并标识内置；自动依赖归入折叠组。
- 详情：简介、依赖、队伍影响。包名与版本常显，包标识、文件位置、完整依赖图按需展开。
- 本轮版本切换：安装指定版本后选择启用，应用前检查实际依赖与队伍影响。后续若添加更新检查，再展示旧版本 → 新版本和变更日志；本轮不显示“可更新／已是最新版”等未经检查的状态。
- 待应用：用户的启停／版本选择暂存为变更清单；校验成功后一次应用到本机新对局。准备失败保留原可用配置，活动对局继续持有原版本。

不再保留第二种行内展开布局作为实现分支。移动端采用列表 → 单包详情的层级导航，避免挤三栏或常驻侧面板。

“添加内容包”提供本地 tgz 和指定 npm 包版本两种来源，先查看包、版本与依赖清单，再执行安装。含新增可执行代码时，在此次安装确认中说明代码来源和权限；不在每个页面重复显示准入复选框。已经准入的包做常规启停或允许的本地编辑，不重新要求准入。

本阶段不实现公共目录服务，也不显示“发现／工坊”商品墙、上传或发布入口。指定 npm 版本可以使用已有的第三方 registry，不代表要建设自己的开放服务。

## 房间内容

从当前房间读取精确的内容描述符，只展示该房间使用的包和版本。此处是只读状态，没有本机启停开关、包安装、升级、授权或同步按钮。

未进入房间时显示空状态。服务器预备的多个固定组合不能合并成一个假想的可用内容集合；建房只能选择服务器实际提供的组合。远程服务器的管理操作属于管理员工具，不开放为普通浏览器包管理 API。

本轮继续不做从队伍报错跳转安装、自动连接本机服务、按房间自动下载／安装包等便捷流程。

## 队伍与操作影响

包详情显示与该包有关的队伍：用到的精灵、技能、特性／纹章，以及停用或升级后哪些引用暂不可用。没有可靠来源记录时，用当前内容目录确定归属；不能只凭名字猜提供者。

停用或缺定义不会改写队伍。队伍页在对应位置显示占位和原始 ID，保留保存、导出、移动；开战前检查目标房间或本机对局的实际内容。缺依赖／版本不符／内容 ID 已移除是不同诊断。恢复同 ID 的兼容定义后重新解析；内容改名须有明确迁移规则，不自动替换。

## 实现结构

应增加一个包级的管理应用层，而不是把 `listContentProjects` 返回值换个名字再显示。

1. **包库**：宿主管理的安装产物与版本。维护来源、内容包元数据和依赖关系；界面只拿稳定句柄。
2. **本机选择草稿**：明确选择的根内容包与版本。自动解析依赖，不直接修改正在使用的安装树。
3. **操作计划**：安装／启停／升级／卸载前，返回依赖增删、冲突、所需代码准入和队伍影响。
4. **准备与应用**：复用现有 npm 检查、准入、私有副本和服务器环境注册机制，在新目录构建候选；成功才发布给新房间，失败保留旧配置。
5. **展示投影**：把底层任务转换成“安装中／需处理／可用／待应用”，保留可展开的详细诊断。

本地能力分别覆盖列包、检查来源、计划安装、计划变更、应用计划和查看操作状态。写操作只走本地 IPC／宿主调用，保持桌面主 frame、登记句柄、受控参数和受控子进程的边界；不增加网络管理服务。前端不能直接拼 npm 命令或任意目录路径。

路由归属：`/content` 改为包级列表与详情，网页端只读，本地端按宿主能力提供写操作；当前项目级界面迁到高级本机服务工具；作者工作区的编辑入口只在本地端提供；房间内容由当前房间描述符投影。现有带令牌的本机开发 HTTP 写入能力不作为新管理器或网页编辑的实现路径；是否移除它属于后续兼容性清理，不能借此开放远程管理。公开服务器内容读取接口继续只读。

## 当前实现

包库、操作计划、组合准备与原子应用已实现。包安装和组合应用均先确认清单；卸载只对已停用版本开放，直接移除受管安装。原有服务器项目管理已移至设置，缺失引用无损保存和开战校验继续保留。当前不包括自动版本发现、变更日志抓取、公共工坊、旧组合目录自动回收和便捷连接／同步。
