# 资源包与环境生命周期 UX 草案

状态：设计提案，待确认后更新交互原型；不是当前功能说明。2026-11-06。

已确定的方向：资源包类似 Forge 模组，环境类似整合包；左右分栏，尽量不整页滚动。本文提出的新增按钮、预检、安装计划和任务能力已在开发用 demo 中模拟，尚未接入正式后端。

## 1. 对象与所有权

| 对象             | 管理单位                     | 用户理解                               | 核心约束                                                   |
| ---------------- | ---------------------------- | -------------------------------------- | ---------------------------------------------------------- |
| 可编辑源项目     | 项目                         | 创作中的源文件                         | 在创作工具中编辑，构建产物才进入安装流程                   |
| 资源包           | 包身份                       | 一个模组                               | 同名的多个版本属于同一包，不把作者或展示名当作唯一身份     |
| 已安装资源包版本 | 包身份 + 精确版本 + 校验信息 | 本机持有的不可变材料                   | 新版本并存；不直接编辑已安装文件                           |
| 环境草稿         | 环境身份 + 草稿修订          | 整合包的编辑配方                       | 包选择、版本要求、来源、规则可编辑；允许保存尚缺材料的配方 |
| 固定环境版本     | 固定版本身份                 | 一份锁定材料与规则的整合包             | 准备成功后不可变，不随草稿和包更新改变                     |
| 使用关系         | 使用目标 + 固定版本          | 本机选用、服务器发布、正在运行的对局等 | 分别展示；没有一个全局“启用”能表达所有目标                 |
| 后台任务         | 操作身份 + 对象/修订 + 目标  | 安装、准备、导入、发布的进度           | 任务失败不是对象消失；取消任务也不等于撤销已提交结果       |

普通 npm 工具库和缓存是实现材料，不全部升级为资源包卡片。资源包的直接与间接依赖必须全部显式出现在环境成员列表中；可标注“用户加入 / 由 A、B 引入”，但不能仅藏在依赖页。此处按第 10 节的用户确认更新。

本机包库、本机离线环境库、服务器工作区不能假设为同一存储。展示当前目标；跨工作区是导出/导入，同一 owner 管理的托管工作区可共享材料。不能因本机已安装就标记远端依赖已齐全。

## 2. 状态不要挤成一条线

对象状态、任务状态、使用关系分别表达。例如：`v1.2 已安装 · 2 个环境使用`，同时可以有 `正在下载 v1.3`，不能用“下载中”覆盖旧版本仍然可用的事实。

### 资源包版本

| 状态/事实                              | 主操作        | 次要操作 / 限制                              |
| -------------------------------------- | ------------- | -------------------------------------------- |
| 尚未安装，已通过包名/文件/环境要求发现 | 安装          | 查看声明、来源与依赖计划                     |
| 安装任务执行中                         | 查看进度      | 在可取消阶段取消；不能重复启动同一任务       |
| 已安装且材料可用                       | 加入环境…     | 选择版本、查看依赖、查看使用关系、卸载此版本 |
| 材料缺失或校验失败                     | 修复材料…     | 给出失败项和来源；不把重装承诺为一定能修复   |
| 有可获取的新版本（实际查到后才显示）   | 安装其他版本… | 显示变更与兼容信息；不自动替换环境中的旧版本 |
| 存在使用关系                           | 查看使用关系  | 分清硬引用与“草稿将无法离线准备”的影响提示   |
| 已卸载                                 | 安装          | 保留与否取决于已登记来源；不虚构在线目录     |

包本身没有“运行中”或泛化的“停用”状态。停用应属于某个环境配方或本机游玩选择。按第 10 节的用户确认，启用必须保持依赖闭包；当前原型的勾选/移出行为需要据此修订，不能允许依赖方留在启用集合而停用其必需依赖。

### 环境草稿

| 状态/事实                          | 主操作       | 次要操作 / 限制                        |
| ---------------------------------- | ------------ | -------------------------------------- |
| 新建、未保存                       | 保存草稿     | 取消；离开时处理未保存内容             |
| 已保存，尚无固定版本               | 准备版本…    | 编辑、复制、检查依赖、删除             |
| 草稿与最近固定版本不同             | 准备新版本…  | 对比变化；旧版本继续可用               |
| 缺少依赖 / 版本冲突 / 来源不可访问 | 解决依赖…    | 可以继续保存；说明具体阻塞项           |
| 正在准备某次修订                   | 查看任务     | 同修订防重复；新编辑不加入已启动的任务 |
| 已有固定版本                       | 查看固定版本 | 编辑、复制、准备新版本、管理版本       |

“准备失败”属于任务，不把仍然保存完好的草稿标记为坏掉；已存在的固定版本继续显示。准备时若有未保存编辑，明确提供“保存并准备”，不能静默准备旧修订。

环境可以保留当前名字，不另造一种“整合包”对象。详情头部展示名称、简介、包数量、最近准备版本；页签为 `内容组合 / 组合规则 / 固定版本`。创建新环境默认包含官方基础内容。

### 固定环境版本

| 状态/事实                              | 操作                                              | 限制                                             |
| -------------------------------------- | ------------------------------------------------- | ------------------------------------------------ |
| 材料可用                               | 选择使用目标…、导出、查看包锁定清单、复制为新草稿 | “已准备”只证明材料准备成功，不冒充完整运行验收   |
| 被本机选择 / 被服务器引用 / 被对局租用 | 查看使用位置、跳转对应管理                        | 不能直接删除；不能替用户停服或中断对局           |
| 材料不可用                             | 诊断 / 检查恢复条件                               | 不允许使用；按原锁恢复且验证身份，否则产生新版本 |
| 无阻塞引用                             | 删除此版本…                                       | 明示影响，后端提交时再次检查引用                 |

“升级”是安装新包 → 改草稿版本要求 → 准备新固定版本 → 显式更新使用目标。“回滚”是选择仍可用的旧固定版本给目标，重新检查兼容与宿主执行政策；不覆写新版本，也不默认回退草稿。

### 服务器使用关系

发布、更新、停止开放、设为默认和解除绑定属于服务器管理，不是包的动作。环境页可提供带目标的入口。开放状态和目标版本分别管理；有更新请求时展示期望版本与实际生效版本。已有对局继续使用捕获的固定版本。

删除环境是有顺序的清理流程：列出绑定/运行引用 → 引导处理引用 → 清理可删除固定版本 → 删除草稿。不能用一个“删除环境”隐式批量停服、删版本。没有版本的空草稿可以直接确认删除。

## 3. 将依赖获取整合进准备流程

用户入口是 `准备版本…` 或 `解决依赖…`，不要求手动逐包复制 npm 名称。

1. **检查当前草稿**：捕获目标、草稿修订、根包要求、来源与网络模式。解析每个目标的直接/传递依赖以及兼容、规则、命名空间冲突。
2. **展示计划**：按“本机可复用 / 需要获取 / 冲突或缺失来源”分组。每项列包名、精确版本、依赖它的包、来源；体积未知则显示未知。明确计划是否需要网络、是否需要凭证。
3. **让用户解决歧义**：来源冲突让用户选来源；版本冲突给出涉及的包与要求，不擅自升级或降级；离线缺材料时提供选择本地文件或切换网络模式的入口。包不兼容、完整性错误、没有权限应分别说明。
4. **一个主按钮**：材料齐全时 `准备版本`，缺材料且计划可执行时 `安装依赖并准备`。获取材料不修改其他环境或本机游玩选择，不自动发布、执行作者代码或运行包生命周期脚本。
5. **分阶段执行**：获取 → 校验 → 装配 → 固定版本提交。只有已有总量的阶段才报百分比，其余显示阶段和当前包。失败可查看原因、返回调整配方、重新检查后重试。
6. **成功后的下一步**：显示新版本，提供 `选择使用目标…` 和 `导出`。不自动开放服务器。

安装计划必须绑定草稿修订、目标与解析结果；执行前重新校验。草稿变化、权限变化、来源或校验信息不一致时要求更新计划，不沿用过期计划提交。

安装部分成功、准备失败时，保留旧可用版本。已校验材料可按缓存策略复用，但展示“材料已获取，环境尚未准备成功”。取消只停止尚未提交的步骤；展示已完成的材料获取，不显示“全部撤销”。崩溃/重启后的任务恢复必须查询真实结果，不能用前端计时器续播进度。

依赖精确版本可以按不同环境分别解析并存；同一环境有不可满足的约束才报冲突。自动依赖不要求用户逐一手动安装，不提供会破坏整个依赖树的随意卸载；清理未使用依赖应走统一回收与引用检查。

## 4. 按钮与布局

维持 B 的固定高度分栏，不增加纵向管理大表单。

- **左侧资源包**：包名/版本/状态，搜索与状态筛选；同包版本通过详情选择器切换。顶部 `添加资源包`。
- **右侧资源包**：`简介 / 依赖 / 使用关系`；固定底栏主按钮 `加入环境…`，材料异常时改为 `修复材料…`；`更多` 放安装其他版本、复制包标识、卸载此版本。未实现的修复入口不能假装成功。
- **左侧环境**：环境名、草稿变化、最近固定版本；顶部 `新建环境` 和导入入口。
- **右侧环境**：内容列表含名称、版本要求、可获取情况；`添加资源包` 打开包选择面板，可从已安装库选择或按来源获取。组合规则独立页签。固定底栏主按钮按状态显示 `保存草稿 / 准备版本… / 解决依赖… / 查看任务`。
- **固定版本页签**：选中一版后显示其内容与使用关系；操作为 `选择使用目标… / 导出 / 更多`。删除收在更多内，并显示阻塞原因。
- **依赖计划**：复用右侧详情区，保留左侧所选环境上下文；可返回编辑。长清单仅栏内滚动，确认按钮固定。
- **任务入口**：页面底部窄状态条 `正在安装 2 项 · 查看任务`；展开任务面板，不挤压成一列历史日志。关闭详情或切换环境不取消后台任务。

若权限不足，操作显示准确的权限原因；宿主不支持的能力不展示可点击假按钮。本机与远端入口在标题和确认计划中均标明目标。

## 5. 与现有实现的差距

已检查的 owning sources：

- `packages/web-ui/electron/content-library.mjs`：`installFile/installNpm` 当前会安装并自动修改本机 desired selection；已有安装暂存/确认和依赖装配能力，但尚无面向上述新流程的统一预检 DTO。新设计不能直接复用“安装并启用”作为纯安装。
- 同文件 `prepareEnvironmentProject` 支持按环境获取/装配、离线开关、已登记来源，并有歧义检查；其临时装配材料不等于用户包库里每个依赖都有独立安装条目。UI 要区分“环境材料可用”和“已登记到包库”。
- `packages/web-ui/electron/local-environments.mjs`：保存、准备、导入导出、版本引用、删除与取消已有入口；本机任务在内存中，按当前实现不能承诺重启恢复或详细下载进度。
- `packages/content-dev/src/content-workspace.mjs`：草稿用 expectedRevision；有固定版本时禁止删草稿；版本删除检查运行租约、保留和导入引用。卸载包检查 active/desired selection，不等同于完整环境影响分析。
- `packages/web-ui/src/types/contentPackages.ts`：已有作者、描述、来源、依赖图、内容统计；许可证、主页、问题反馈与兼容声明尚不能直接从当前列表接口完整取得，原型展示是提案示例。
- `docs/v4/unified-management.md`：服务器任务、导入恢复、发布与运行引用有更完整合同；不能将其恢复能力直接归给本机环境库。

## 6. 先验证这些情景

1. 首次安装 A 自动取得依赖 B，但不改变已有环境与本机当前玩法。
2. 两个环境分别需要 A v1/v2；安装 v2 不修改环境一和它的固定版本。
3. 更新草稿后准备失败，旧版仍能使用，草稿仍可继续编辑。
4. 资源包安装条目被卸载时，分清草稿未来准备受影响与独立固定材料仍然可用，不虚报固定版本被删除。
5. 依赖离线缺失、来源失效、权限不足、版本冲突分别有可执行的下一步。
6. 下载完成但准备失败/取消，能说明保留了什么；提交后不能宣称撤销成功。
7. 草稿在计划后改变，后台不把新配方混进旧计划；任务结果归属原修订。
8. 有服务器或运行租约引用时删除被阻止，界面展示引用目标，且并发操作最终由后端重检。
9. 固定材料损坏不能靠改包版本“修复”同一固定身份；恢复必须遵循原锁与完整性。
10. 本机安装完成不代表远端已具备材料；导入到另一个目标不得覆盖同名环境或隐式发布。

下一步：先在 demo 模拟“安装计划 → 安装依赖并准备 → 固定版本 → 使用关系/删除阻塞”这一条完整流程，明确这些交互后再接真实能力。尚不新增归档、自动更新、自动发布、评分市场等独立功能。

## 8. npm 版本解析与安装状态（补充提案）

### 四层分开

1. **作者依赖声明**：用 npm `dependencies` / `peerDependencies` 与 semver 范围表达需要什么。精确版本仍允许，但代表作者有意限制，不把所有包自动钉死，也不擅自放宽作者声明。
2. **环境配方**：声明根内容包与基础内容的版本要求、显式来源。可用范围，也可选择固定版本；修改范围是草稿编辑，不改变已准备环境。
3. **环境解析结果**：每个环境有自己的 npm lock，保存具体版本、位置、来源、integrity 和依赖边。两个环境可以用同一包的不同版本。一个包的 peer 上下文也属于解析结果，不能仅凭“包名@版本相同”就复用整个装配目录。
4. **准备快照**：绑定配方修订、lock 摘要、实际内容/资源/规则与运行兼容身份。对局使用这份不可变结果。“固定”描述解析结果，不表示作者只能声明精确依赖。

不移除 lock 来解决冲突。已有 lock 且配方未变时优先重现原树；主动更新依赖才运行新的解析，并展示 diff。按 lock 恢复用 npm ci 语义；输入不匹配时失败，不偷偷更新。目录缺失不等于需要更新依赖版本。

### npm 能解决和不能解决的事

| 情形                                                | 建议行为                                                                                                   |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| A 用普通 JS 库 C@^1，B 用 C@^2                      | npm 可在不同路径安装多个版本，保留各自解析边；不要求全局只安装一个 C                                       |
| 两个环境分别需要内容包 C@1 / C@2                    | 环境独立解析、独立准备，可以同时存在于材料库                                                               |
| 同一环境内两个内容包都需要共享 C，范围有交集        | 交给 npm 解析，目标是共同使用满足要求的内容提供者；实际树仍需内容层校验，不能把“范围有交集”当成树一定去重  |
| 同一环境内 C@1 / C@2 都注册相同内容身份或 namespace | 阻止准备，列出引入链与版本约束；嵌套 node_modules 只能解决模块寻址，不能消除游戏内容 ID 冲突               |
| 同内容版本在两个位置重复出现                        | 当前加载器同样拒绝重复内容身份；需要解析/去重后重检，不静默覆盖注册                                        |
| 作者只声明兼容基础包 4.1.0，但环境请求 4.2.0        | 保留旧环境，提示不兼容；选择兼容的作者包版本、调整环境基础包要求，或拆成不同环境。不能把下载成功当成可运行 |

当前证据：`packages/pack-loader/src/npm/inspect.ts` 已以 npm ls 与 lockfile v3 校验真实安装树，核对 dependencies/optionalDependencies/peerDependencies；按路径保留依赖边。所有带 Arcadia 内容声明的节点会参与内容检查，并拒绝重复 projectId/namespace（`CONTENT_VERSION_CONFLICT` / `NAMESPACE_CONFLICT`）。`npm/prepare.ts` 区分普通库与内容注册依赖。这不是新引入 npm，而是把现有解析和内容准入的关系明确表达出来。

不能把一般 npm 库的“磁盘上可安装”扩大成作者运行沙箱一定支持所有 Node API。Effect 闭包构建、SDK 与宿主兼容仍有独立检查。

### 共享内容采用什么依赖模式

建议把**期望与环境共享的内容提供者**（例如基础内容包、共同扩展包）表达为 `peerDependencies` 兼容范围，由环境明确提供；纯内部工具库继续用普通 `dependencies`。必需 peer 不标 optional。并非所有内容依赖必须立即迁移为 peer，但旧普通依赖导致重复内容注册时必须明确诊断。

npm 的 peer 机制不是全环境 singleton 声明；真实安装树仍可能产生多个 peer 上下文。必须继续内容身份唯一性检查，不能仅凭 peer 字段就认为问题解决。默认不使用 `--force` / `--legacy-peer-deps` 或自动 overrides 掩盖不兼容。高级 override 即使以后开放，也应是可审计的配方变更，并继续接受完整内容/运行兼容检查。

基础内容如果仍由宿主内置注入，需要参与相同的“环境提供了哪个具体版本、作者要求哪个范围”的兼容检查；不能仅加 peerDependencies 就声称已经改成 npm 统一管理。当前 `packs/base` 是预发行版本，范围示例和更新策略要考虑 npm semver 的预发行匹配语义，不把 preview 自动等同于稳定 4.x。

### 基础包升级与重现

- 基础内容也有具体版本和材料身份，不在固定快照里写“随游戏更新”。原型已改成明确的示例基础包版本。
- 客户端升级可以提供更新的内置材料，但不能静默替换旧快照引用的基础内容。
- “更新基础内容”在草稿中发起新的依赖计划，展示作者包的兼容约束，成功后生成新快照；旧快照仍指向旧材料。
- 旧材料不可获取时说明缺失，不用最新基础包代替。旧快照也必须满足当前运行宿主/SDK能力；材料精确并不保证任意新引擎都能运行。
- 版本范围属于兼容声明，并非语义兼容证明。作者错误地放宽范围仍可能造成玩法变化，需要运行校验，不宣称 semver 自动证明正确。

### 当前安装状态入口

原型新增“安装状态”：本机当前选用的固定版本、直接安装条目、自动依赖、缺失/需处理状态、对应草稿与独立固定副本数量，以及任务阶段。可跳转安装计划、卸载影响与版本引用。这里统计的是 demo 的材料库，不冒充实际 npm 全树与磁盘占用。

正式实现应提供两个视角：

- **材料库视角**：具体安装材料是否存在/校验有效、来源、直接安装或自动引入、可回收情况。缓存存在不代表任意环境已经装配完成。
- **环境视角**：配方要求 → lock 实际解析 → 当前安装树是否匹配 → 准备快照与本机/服务器使用关系。显示依赖的引入链、真实安装位置及 peer 上下文，不把 npm 树扁平为一个包名对应一个版本。

修复安装默认按既有 lock 恢复；更新依赖是另一个显式动作。自动依赖回收必须检查真实保留根和材料共享关系，不能按“没有草稿勾选”删除。原型暂不提供假装能安全回收的按钮。

下一步真实接口应返回 requirements、lockIdentity、解析节点/边（含位置和 peer 关系）、材料状态、引用与阻塞原因。demo 当前固定示例解析不承担 semver 求解，不在前端自写 npm 替代算法。

参考：

- [npm package.json：dependencies、peerDependencies、overrides](https://docs.npmjs.com/cli/configuring-npm/package-json/)
- [npm install：范围与 lock 的关系](https://docs.npmjs.com/cli/v11/commands/npm-install/)
- [npm ci：按锁重现](https://docs.npmjs.com/cli/v11/commands/npm-ci/)

## 9. 入口语义修正：下载与安装中心

用户所说“安装状态管理”指下载进度管理，不是已安装资产清单。主入口调整为“下载与安装”，汇总正在下载、校验、安装/准备、排队、完成、失败和已取消任务；提供取消、移出队列、重新检查重试、查看结果与清除结束记录。原本机材料清单退为资源包详情的次要入口。

原型以串行队列演示，下载进度与 MB 均显式标记模拟。下载进度完成不等于安装完成，校验/装配阶段另行展示；无网络获取的任务显示“使用本机材料”。不提供后端尚未支持的暂停/断点续传承诺。真实接入时仅展示后端已知总量，未知大小时显示阶段进度，不猜测百分比、网速或剩余时间。

已用浏览器验证：启动下载、添加等待任务、移出队列、完成筛选和清除结束记录；组件严格类型检查通过。

## 10. 用户确认：环境内资源包单版本、显式成员与依赖启用

本节取代此前关于隐藏间接资源包或仅在加载时检查冲突的较弱提案。原型现已按第 11 节模拟这些约束；真实 npm 与后端尚未接入。

### 确认的合同

- 每个环境中的一个资源包身份只能对应一份逻辑实例、一个具体版本。所有消费者都指向它；不能借 npm 嵌套安装私有资源包副本绕过约束。
- 直接和传递资源包依赖都显式列入环境成员集合，并展示被哪些包引入。显式可见不等于用户亲自添加：保留用户意图与依赖来源，避免所有自动成员永久变成手动保留根。
- 所有对该包的版本要求与环境自身要求必须共同满足。精确要求不是一律禁止：相同精确版本或与范围兼容可以；不同精确版本、全体范围无共同可用版本必须报错。
- 必须检查全体约束，不只做两两相交判断；多个带 `||` 的范围可能两两相交却没有全体共同解。即使范围有理论交集，也需要实际可取得且满足宿主策略的发布版本。
- 启用资源包时连同其必需依赖一并进入启用计划，按依赖顺序装配。停用某依赖时，应阻止单独停用并列出依赖方，或提供明确确认的“同时停用这些依赖方”。普通取消勾选不能静默留下破损配置。
- 删除依赖方后，自动引入且不再被使用的成员可成为清理候选；用户主动保留的成员不自动移除。材料回收与环境成员删除仍是不同操作。
- 基础内容包服从同一版本交集和显式成员规则。其他环境可选不同版本，但一个环境内不存在双基础包。

### npm 生态的对应实践

1. **npm peerDependencies**：Node.js 官方转载的设计文章以 Grunt、Chai、Winston 等插件解释了为什么多个私有宿主副本不可行，并展示两个插件对 Flatiron 的版本约束冲突。与本项目“资源包互相扩展同一共享内容”的关系最直接。当前 npm 的 strict-peer-deps 可以将 peer 冲突作为安装失败。
   - https://nodejs.org/en/blog/npm/peer-dependencies/
   - https://docs.npmjs.com/cli/v11/using-npm/config/#strict-peer-deps
2. **JupyterLab 扩展系统**：sharedPackages 的 singleton 与 strictVersion 分别控制共享单份依赖和版本范围校验。这是与资源包平台接近的真实插件宿主；它不提供本项目所需的环境显式成员/启停闭包管理。
   - https://jupyterlab.readthedocs.io/en/stable/extension/extension_dev.html#deduplication-of-dependencies
3. **webpack Module Federation**：singleton + requiredVersion + strictVersion 明确表达共享唯一实例与拒绝不兼容版本。它侧重运行时共享与选择，不能当成安装前全体约束求交求解器；默认 singleton 的选高版本/警告策略不足以满足这里的要求。
   - https://webpack.js.org/plugins/module-federation-plugin/
4. **Yarn Classic --flat**：历史上明确支持每包只安装一个版本，用户选择写入 resolutions。可以借鉴单版本目标，但不是要求迁移到 Yarn 1；强制 resolution 不代表同时满足所有声明，不能作为兼容证明。
   - https://classic.yarnpkg.com/en/docs/cli/install/
   - https://classic.yarnpkg.com/en/docs/selective-version-resolutions/
5. **Yarn Constraints / Rush**：在 monorepo 中检查依赖声明版本一致。Yarn 当前约束文档明确不覆盖传递依赖，Rush 的同范围要求也不同于“允许不同范围但存在共同版本”，因此不能直接替代环境求解。
   - https://yarnpkg.com/features/constraints
   - https://rushjs.io/pages/configs/common-versions_json/

### 建议落地方式（尚待实现）

资源包作者用 peerDependencies 声明共享资源包约束；环境管理器把完整资源包依赖闭包提升成环境根 dependencies，并记录每个成员的引入原因。所有成员位于同一个环境根层级，普通工具库不因此自动成为游戏资源包。

npm 负责获取/解析与 lock，使用严格 peer 校验；环境管理器另行校验资源包身份唯一、全体约束、显式成员完整性、依赖启用闭包与当前内容准入。不给 force/legacy-peer-deps 自动绕过冲突，也不自动 overrides 强压错误版本。

递归发现依赖时可能因候选版本变化而引入新的约束，需要联合重新解析并检验完整树，不能简单“先取最新版本，再逐个补依赖”。不要把 npm 的某次求解失败直接称为所有可能版本均无解；诊断应区分当前选定版本冲突和发布版本候选是否穷尽。实现前可用离线测试包验证根 peer 聚合、传递 peer 提升、预发行、同版本重复位置与真实无解情形。

输出 UI 示例：A 要求 C ^1.2.0、B 要求 C >=1.5.0 <2.0.0，若可用则统一选择 C 1.6.3；环境列表同时显示 A、B、C，C 标记“由 A、B 依赖”。若 B 改为 ^2.0.0，阻止提交新计划，列出 A→C 与 B→C 冲突，不安装两份，也不损坏旧环境。

循环必需依赖的启用集合可以形成闭包，但不一定存在合法装配顺序；应按内容加载合同检查并返回循环路径，不能用随意排序伪装依赖顺序正确。固定快照仍锁定成功解析的结果，不能取消锁定来规避冲突。

## 11. 显式共享资源包交互验证

原型已按第 10 节增加环境成员集合与直接启用来源的区分。自动资源包也显示为独立成员，标注依赖方；同身份的新版本替换旧成员版本，不能同时出现两份。停用保留成员行，准备快照只包含依赖闭包完整的启用成员，并按依赖顺序列出。

示例目录包含自然基础 1.6.3 / 2.1.0、森林奇遇（^1.0.0）、竞技拓展（>=1.5.0 <2.0.0）和荒野挑战（^2.0.0）。候选兼容集合是明确列举的演示数据，用于验证 UX，不是 npm/semver 通用求解器。

浏览器验证通过：森林与竞技只引入一行自然基础 1.6.3；加入荒野挑战显示三条要求并拒绝变更；“保持启用”不更改组合；“同时停用依赖方”会停用森林和竞技，保留独立启用的内容；随后加入荒野会选择唯一自然基础 2.1.0，安装并准备后的快照包含正确依赖及版本。1280×720、390×844 无整页滚动。原型组件严格类型检查通过。真实 npm 根依赖提升、版本范围联合求解和服务端启用约束尚未接入。
