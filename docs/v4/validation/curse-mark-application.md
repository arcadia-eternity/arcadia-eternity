# Curse random status application

`createCurseMarkApplication` implements `effect_mark_curse_add_random_status` using the existing authoring selectors. The injected ordered mark catalog is retained by identity; `selectFrom([marks]).flatMap(catalog => [...catalog.values()])` reads membership at execution, filters current `status` tags, fully shuffles with battle RNG, then takes the first item. It shares the owner query and addMark operator. No runtime parser or DataRepository dependency is introduced.

This intentionally differs from passing a fixed list of catalog values to selectFrom. Additions, deletions, replacement definitions and tag changes before execution must be visible, as they are to the old dataMarks selector. Catalog iteration order is part of the deterministic RNG contract. The production environment must supply its own ordered catalog rather than a process-global repository. This factory does not seal that catalog or close its downstream dependencies.

The unchanged YAML is the independent reference; no source correction is required. The ledger pins the original definition, complete ordered mark catalog and all nine currently eligible status definitions with their downstream effect IDs. Its classification remains U until those dependencies and production admission are complete. Tests retain official dependency configurations while replacing their effects with empty lists only to isolate application behavior.

The 19 focused tests execute real RemoveMarkPhase, covering ordinary removal, suppression/inactivity/indestructibility, repeated removal, collection cancellation, add cancellation, owner changes, existing marks, changed options, empty/singleton catalogs, reversed order, execution-time catalog deletion/addition/replacement and tag changes. Each variant runs three seeds against the unchanged legacy effect and independently checks the next RNG draw. An additional deterministic sweep selects every official status and verifies that the source remains active during creation and is detached after removal. Empty or singleton status sets consume zero draws; N eligible definitions consume N-1 draws. Cancelling the collected effect consumes no draw, while cancelling creation after selection retains the shuffle consumption.
