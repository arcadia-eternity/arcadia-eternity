# Weakness speed binding acceptance

The reviewed value contract in issue #205 says a binding capture of an empty selection stays empty; captured entities remain readable while benched, while a destroyed entity becomes missing. The latter is a deliberate difference from retaining a removed legacy attribute source. This record identifies that difference as **C20**, specific to `effect_mark_reduce_speed_ruodian` and its captured mark input. It does not select a replacement instance or change to position following.

Three actual-domain cases in `weakness-speed.test.ts` supplement the earlier mechanism examples:

- The production `mark_ruodianjihao` source is not in its owner's marks during OnMarkCreated. Both unchanged legacy YAML and the native effect select an empty collection then. The native capture remains empty after insertion; merge is not another creation event. Creation/merge/suppression/switch/destruction/replacement all retain the original 300 speed and 340 special defense in the fixture. The creation observer explicitly confirms membership is false. This preserves an inactive original rule, not a claim that ordinary placement reduces speed.
- When a separate trusted source observes an already existing two-stack weakness mark, both implementations first produce 250 speed. Direct removal leaves the old mark's stack at two. Legacy retains the captured -50 attribute source; native follows the reviewed missing-input policy and suspends it, returning speed to 300. Replacing the weakness mark does not rebind either captured identity. Destroying the observing source releases its contribution in both versions.
- A normal-selection runtime snapshot of the actual source-mark binding restores through a fresh catalog/host without another creation event and preserves the empty binding capture. Stack consumption after restoration matches uninterrupted execution. Every case releases its attribute systems.

No production execution order, mark collection insertion or binding runtime was changed by this characterization.
