# Immutable content environment foundation

`lockContentEnvironment` independently compiles received JSON texts using the built-in trusted capabilities, rejects conflicts, then publishes a frozen environment. It never mutates an existing room during compilation. The current pack compiler admits pack-local references only, so this initial environment composes closed packs; cross-pack imports, official species/skill catalogs, custom trusted plugins and network room negotiation remain pending.

Build identity is generated by `scripts/build-battle-environment.mjs`, now invoked by the battle code build. It emits `dist/environment-runtime.mjs` and `dist/environment-build.json`. Core and registry identities use domain-separated SHA-256 hashes of the entire bundled executable artifact, including dependencies, schemas and restoration code. They conservatively change together when the artifact changes. No Function.toString, manually assigned effect versions or ID-only hashes are used. The bundler working directory is fixed to the repository root; invocation from root or package directory produces the same identities. Hosts must obtain this manifest from their trusted build; accepting a peer's claimed build identity as host authority is not supported.

The manifest includes the trusted build identities, a policy digest, a sorted pack set of normalized content digests, and the final environment digest. Normalization uses the actual compiler result (including defaults and parameter references), sorts object keys and preserves array order. Separate transport digests identify the exact received UTF-8 texts. Whitespace/default spelling can differ while semantic identity remains equal. Rules and action order remain significant. Duplicate pack IDs and overlapping mark/effect/action IDs are rejected rather than overwritten.

Policy bounds are 32 packs, 1 MiB per text and 4 MiB total, checked before JSON parsing/compilation. Existing compiler bounds still apply inside each pack. Hashes establish consistency, not code authorization; inputs contain data, not executable capabilities or schemas.

Each environment installs one aggregate parameter catalog into a Battle after collision preflight and binds that Battle to its environment instance. Reinstallation or switching environments on that Battle is rejected. Snapshot wrappers require the bound environment, and the snapshot catalog revision is the environment digest. A sealed SnapshotCatalog prohibits later content/effect/value/binding registration. Restoration uses the matching catalog and existing snapshot config state without reinstalling parameters. A newly compiled environment with the same identity can restore the old snapshot; a different identity is rejected.

Nineteen tests cover byte-level build identities, independent transport/semantic hashes, compiler default normalization, pack-set and action ordering, build/content mismatches, malformed or oversized inputs, conflicts, asynchronous input mutation, atomic installation, sealed registration and two same-ID rooms with different content. The two-room scenario closes one room, keeps the other working, then restores the first room through fresh compiled definitions and checks captured mark parameters.

`node scripts/verify-content-environment.mjs` verifies artifact bytes before directly importing the artifact in Node and loading that same artifact in real Chrome. Both hosts compile the same pack to the same environment/transport identities; Chrome also normalizes round-trip data and rejects a changed registry build. This proves the standalone environment artifact is executable consistently. Existing game/server/CLI hosts are not yet switched to it, and the artifact's entire module graph has not yet met the final no-legacy cutover gate.

The existing SnapshotCatalog-based API remains available to legacy hosts. Environment-bound snapshots currently cover the effects/marks in these closed UGC packs; official species, skill definitions and dependencies still need to be admitted into the same immutable environment before final migration acceptance. No production loader or room protocol has been switched. Standards review found no blocking issue; independent Spec review remains pending its existing availability limit.

Verification: code/declaration builds, V4 typecheck/lint, all 915 tests across 33 V4 files, source provenance, existing Node/Chrome checkpoint checks and the standalone environment artifact check pass.
