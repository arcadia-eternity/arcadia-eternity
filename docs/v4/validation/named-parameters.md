# Named parameter modifiers

Nine native candidates resolve their original configKey aliases through the parameter catalogs of their existing consumer effects. The factory accepts catalogs keyed by dependency effect ID, validates every named reference while constructing the effects, and captures resolved canonical addresses. It does not install parameters, create a second configuration store or rewrite production YAML. The standalone rage candidate supplies its existing catalog; generated authored consumers supply effectParameters(effect).

ParameterCatalog.addressOf exposes only address resolution. The shared addParameterModifier operation delegates installation to ParameterCatalog.modify, retaining its allowed-operation check. Named and tagged operations share amount→priority sampling per target, ownership checks and source-mark cleanup. Repeated execution appends modifiers; effective state remains in the battle's ConfigSystem. The nine literal increments keep their original values, including negative increments and the 0.5 multiplier change.

## Assembly boundary

Install each required consumer catalog before dispatch. Missing catalogs or unknown aliases fail during assembly. A known but uninstalled canonical key fails during execution rather than registering the legacy operator's temporary zero placeholder. This is the native assembly contract, not parity with legacy's incomplete-registration fallback. No alias-named shadow key is created. Tests check defaults against the original raw:number definitions and read aliases through the actual consumer catalogs.

## Scope and timing

All candidates retain self, selfPlayer or opponentPlayer selection. The existing ConfigSystem source-owner compatibility rule remains active: the three opponentPlayer modifiers are stored but do not affect opposing reads. A selfPlayer modifier also remains restricted by its source owner's scope rather than applying automatically to every team member. These are measured historical behaviors, not claims that the descriptions' opposing bonuses are effective; resolving that scope mismatch remains necessary before production acceptance.

Tests cover skill and mark sources, repetition, late base-value and ownership changes, cancellation, suppression/recovery and removal. They compare six effective scopes, stored modifier counts and RNG continuation against unchanged YAML with the legacy alias key registered. The native side uses real parameter catalogs from the rage, attribute, damage, dynamic contribution, mark application and vital sequence candidates. Mark application dependencies are identity-only fixtures for catalog assembly; downstream mark effects are not inferred from this validation.

Two actual consumer checks go beyond config reads. The rage candidate gains 25 while the +5 source exists and returns to 20 after cleanup. The critical-rate candidate captures its configured factor on installation while following its source mark stack: removing the +5 source does not change an existing captured 25 factor, changing stack still updates the contribution, and a subsequent application reads 20.

Candidates and source hashes are recorded separately from production admission. Per-candidate full-game and fresh-catalog snapshot continuation, dynamic modifiers and the source-scope mismatch remain outstanding.

Validation: 130 focused named-parameter checks plus 113 tagged-parameter, catalog and authoring-snapshot regressions pass against the isolated public bundle. V4/design typechecking, V4 lint, declaration generation, provenance and reproducible historical audit checks pass. Coverage verifies all nine source hashes and reports 1047/1065 candidates.
