# UGC boundary integration validation — 2026-10-29

Integration branch: `codex/ugc-client-boundaries`, based on `refactor/v4` commit `7105ca1cc10768dc743ccad9b6d623531ade3163`. Issues #248–#254 remain open until their remaining acceptance work is complete. No production deployment or package publication was performed.

## Implemented boundaries

- Browser authentication, APIs, sockets, catalogs and battle reports resolve the deployment configuration before application startup. Browser URL/history preferences cannot override it. Paired and explicitly split deployments remain supported.
- The server distribution includes the paired website, with explicit headless mode and API-aware SPA fallback. A build without Git metadata was also exercised.
- Remote clients consume the server's complete public catalog, content-only locales and declared presentation assets. They do not install the server's executable packages. Transport limits, no-store requests, fixed room environments and optional-media fallbacks are enforced.
- Desktop remote play uses the bundled application in a separate temporary session. All legacy management IPC handlers check the actual management main frame. Remote windows cannot install packages, read workspace files or start local hosts.
- Browser SWF playback uses an opaque restricted iframe and pinned local runtime. Desktop SWF playback uses isolated hidden offscreen renderers, forwarding bounded native paint frames into DOM canvases. Existing battle protocol messages and authoritative calculations are unchanged.

## Shared preparation lifecycle

Production desktop refresh exposed concurrent local initialization from application bootstrap and the mounted battle page. A late local metadata result could replace an already accepted server catalog while retaining the remote-content flag, leaving unknown portraits and no SWF players. Controlled delayed-loader tests reproduced both duplicate initialization and the late overwrite. The resource store independently reproduced duplicate base reads and stale success/failure writes after reset.

Preparation belongs to the data/resource stores. Concurrent consumers share the current initialization task, and pages wait for current readiness. Explicit reset/reload and display-scope transitions own invalidation; individual component lifetimes do not own shared cancellation. Recovery prepares the current room's catalog before installing battle state, with validity checks before asynchronous results mutate the active display. This is live-task sharing within the current scope, not a shared or persistent UGC asset cache.

## Review and limitations

Independent standards/specification reviews found and led to fixes for remote media fallback crossing the selected environment, placeholder sprites failing to mount, and duplicated native-bounds publishing. A subsequent read-only review of the offscreen transport found no blocking issue in source authentication, bounded buffering, stale-task guards or lifecycle cleanup. Runtime evidence is still required on each release platform; code review is not a security proof.

The repository-wide test run did **not** complete successfully. The large battle suite produced default five-second timeouts under the concurrent workload, and the run was interrupted. Three selected damage-modifier cases subsequently passed with one worker and the original timeout; this does not establish that every full-suite failure was pre-existing. Three P2P battle tests fail with `runInMemoryP2PBattleE2E is not a function`; that exact failure was reproduced on the unchanged base checkout. These results must remain visible in review rather than being represented as an all-green suite.

Docker execution was unavailable. Signed installers, upgrade/signing/notarization, Windows/Linux offscreen behavior, physical audio timing, a broader hostile binary SWF corpus and sustained resource-pressure tests remain unverified. Current watchdog and transport limits do not provide hard CPU or heap quotas. Shared runtime manifests and duplicated cross-runtime playback contracts remain maintenance follow-ups.
