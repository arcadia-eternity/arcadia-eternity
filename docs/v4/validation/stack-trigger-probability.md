# Stack-following trigger probability

`createStackTriggerProbability()` owns `effect_mark_increase_skill_trigger_rate_with_stack`, compared against unchanged source YAML. Historical `addTaggedConfigModifier` accepts the ReactiveValue returned by `selectAttribute$('stack')`; its contribution is not sampled at creation. The native definition explicitly captures the source mark for the binding lifetime and follows that instance's stack. No RxJS dependency is added.

The reusable `ops.bindTaggedParameter` adapter installs an existing authored value plan into ConfigSystem, scoped to each selected Pet or Player. Tags match registered keys at application time, including canonical parameter addresses; future registrations do not join. Each matched key receives an independent append-only contribution and capture state. The source mark owns cleanup. Scope hierarchy, source suppression and modifier ordering still belong to ConfigSystem. The adapter requires a mark source, as do existing persistent authored attribute bindings; it is not a general adapter for malformed skill-source invocations of this mark effect.

Bound parameter values use the same evaluation, missing-input, finite-number, capture-state and dependency machinery as attribute contributions. An unavailable live contribution is skipped and can recover; disposal completes its subscription. Direct and transitive live reads of the destination parameter and cross-battle configuration reads are rejected. A capture may read its destination once without creating a live edge. This extends typed binding targets with a scoped parameter target rather than fabricating an attribute target.

Snapshot restoration recognizes parameter binding targets and validates the actual config store, scope, parameter key, source mark and exclusive ownership of the value before activation. Static code identities are registered through `effectAuthoring.registerEffect`, alongside the authored binding definitions. Fresh-catalog restoration retains stack-following behavior and source cleanup. A tampered destination key is rejected.

Validation: seven differential scenarios cover normal/repeated installation, late registration, absent tags, suppression/recovery, source destruction and switching active pets. Four additional scenarios cover capture/follow selection crossed with capture/follow attributes, including stat mutation and opponent switching. Dedicated tests cover fresh-catalog snapshot continuation and cleanup, tampered snapshots, direct/transitive parameter cycles, non-finite contribution detachment/recovery, and actual mark-creation phase installation. Sixteen focused tests pass. With tagged/named parameter, authoring-boundary, authored-snapshot, value-binding, parameter-catalog and general snapshot regressions, 295 unique checks pass; the authoring-design suite passes 87 more. Type tests require a persistent numeric plan and Pet/Player scopes.

Candidate ownership is not production admission. Full-game dependency acceptance and production catalog replacement remain outstanding. No source YAML was rewritten.
