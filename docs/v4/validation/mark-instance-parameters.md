# Mark instance parameter lifecycle

This slice implements the runtime path for #223 G. It does not yet expose an `addMark` action in the bounded UGC registry.

Trusted content calls `defineMarkInstanceParams(baseMark, schema, slots)`. The closed TypeBox object describes finite scalar fields and defaults; each field declares an effective schema and allowed Config operations. There are at most 64 fields. Optional fields and missing defaults are rejected, so every instance has a complete normalized identity. The definition copies author metadata and cannot be replaced after registration. Standard BaseMark definitions are supported; specialized subclasses such as stat stages retain their dedicated implementation.

Install the returned `parameters` catalog in the Battle ConfigSystem before use. Keys are `ae:mark-param:[baseMarkId,field]` (JSON encoded). They identify a field on a content definition; the Mark instance is the Config scope. `read(config, mark, field)` checks the source definition and works directly on a newly created Mark before it is in the owner's marks collection.

`AddMarkContext` accepts `instanceParams` as its last constructor argument. It validates, defaults, copies and freezes those values when the add request is made. The source skill can subsequently change its own inputs without changing the incoming mark. After OnBeforeAddMark, the operation validates against the final base and target. If a same-ID mark has different normalized base parameters, `Battle.addMark` returns `parameter-conflict`, without mutex removal, stack writes or creation. Cancellation still takes precedence.

Compatible parameterized marks retain the existing instance and its parameters even in a mutex group; other mutex conflicts follow the existing removal flow. StackStrategy still controls stack/duration behavior. Effective Config modifiers do not participate in compatibility identity. Legacy marks without declarations retain the old mutex/stack path and reject supplied instance arguments.

For a fresh instance, its base parameter values are installed in its own Config scope after ownership is assigned and before OnMarkCreated. Subsequent effective changes use the existing scoped Config modifier API. Destroy hooks can still read parameters; scope values and modifiers are released afterwards. An exception during creation also releases the newly installed scope. No live dependency or cleanup is attached to the originating skill.

Snapshots persist instance parameters and scoped Config values. Parameterized BaseMark content must be explicitly registered in the revisioned SnapshotCatalog, so loading cannot silently recreate a prototype without its executable contract. Export and restore compare normalized identity with the saved scope, reject missing/mismatched state and freeze the restored base record. Restore does not replay creation or overwrite effective modifiers. The content revision remains the host's responsibility, as with existing native effects; automatic manifest hashing is a separate incomplete gate.
