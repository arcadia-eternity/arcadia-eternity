# 当前项目的内容约定

这些是当前 base 包的适配方式与调查入口，不是原作服务端规则。目标仓库发生变化时以当前定义和实现为准；机制与数值来源仍遵循 SKILL.md 的采用口径。

## 技能与学习列表

- 必杀技：当前 `data/skill.yaml` 中 Climax 技能统一配置 `sureHit: true`。接入时沿用明确的必中字段，不用把 accuracy 写成 999 来替代；旧表命中 100 本身不能证明必中。具体技能存在相反证据时单独说明。
- 隐藏技能：当前种族学习列表以 `hidden: true`、`level: 60` 表示。原表特殊学习条件编码不能直接当作实际等级；将原作解锁条件留在来源记录，不在单只精灵任务中扩建解锁系统。
- 默认补齐目标形态的完整正常玩家前置进化链，各阶段使用自己的原表学习列表；进化形态另外继承前置技能，保留学习等级并按技能 ID 去重。为每个阶段接入种族、文本、资源和进化关系，不向幼体直接复制进化后的技能。用户明确只要单一形态时才仅继承技能而不接入前置种族。搭档、同系列或同名形态不自动属于进化链。

## 复用前查清语义

- 建立本次目标的小型对照：原始精灵/技能/buff/道具 ID → 当前 species/skill/mark/effect ID。原始编号属于不同命名空间，不能直接互换。
- 同名技能先核对当前实现的触发条件、阶段变化、概率和数值；已有实现可能包含项目修订，不能仅凭同名就宣称与原作一致。共享定义与目标需求冲突时明确取舍，避免顺手改变所有使用者。
- 除名称搜索外，按机制找现有实现。例如跨精灵印记联动可调查极光/绝影相关效果，比较印记归属、触发时机、消耗和换场行为后再决定复用。存在类似机制不代表语义相同。
- 联动涉及队友时，专项测试尽量通过队友实际技能产生印记，再换场触发目标效果，覆盖完整联动链。

## 不能从一个案例推广的配置

印记层数上限、换场是否清除、重复施加是刷新还是叠加、替代印记是否消耗、持续回合及伤害类别都影响玩法，必须逐项按资料确定。不要把实验中的“最多 5 层”“换场清除”或“不消耗”写成默认规则，也不要以“配置保护”为理由添加未获依据的玩法上限。

配置了 refresh 等策略只能证明实现选择；当重复施加会改变核心机制时，应验证实际效果。报告区分资料明确说明、当前项目适配和本次实现取舍。

## 验证边界

不维护写死的全包精灵、技能、印记或效果总数。验证 ID 唯一、引用可解析、注册完整及实际行为；比较两条加载路径时可比较内容 ID，验证新增一个模板时可比较相对增量。CLI 展示内容数量可以保留，展示值不作为固定内容规模的验收门槛。

默认不运行客户端试玩或 Web UI 测试；按 SKILL.md 进行内容与战斗验证。

## 已确认的项目统一行为

基础不良状态复用 SDK/base 的公共印记。冻伤降低特攻能力是项目有意统一的行为，不因资料使用“特攻伤害降低”的文字就重复判为复刻缺陷。其他共享定义仍逐项核对，不将这个决定推广到所有差异。
