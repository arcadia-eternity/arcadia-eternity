# 精灵复刻的测试组织与写法

以下路径相对 Arcadia 仓库根目录。适用于当前 base 内容包；用户明确要求独立内容包时，遵循目标包现有测试入口，不把外部包测试塞入主仓库。

## 独立 SDK 包

测试放在包内 `test/*.test.mjs`，使用 Node test runner 和 `prepareContentPack`，跟随模板现有 npm scripts。使用真实依赖闭包，不借主仓库 node_modules 或自写 base 专用加载器。包内构建后执行 check/test/pack；主仓库的 pnpm 命令不适用于独立包。测试与 debug 队伍不进入运行时 tarball。

## 主仓库测试放在哪里

| 内容                                       | 位置与范围                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 精灵技能、印记、特性、纹章及联动           | `packages/battle/test/v4/<group>.test.ts`；名称与内容分组或效果模块对应，例如 `kadundudu.test.ts` |
| 同一进化链的幼体与进化形态                 | 扩充同一个分组测试文件，不逐形态另建目录或重复整套测试                                            |
| 已有共享机制的缺陷回归                     | 放入负责该机制的既有 V4 测试文件；只有新增通用机制才建立对应机制测试文件                          |
| 多个测试确实共享的稳定辅助函数             | 优先复用当前 `test/v4/` 辅助模块；需要提取时用清晰名称的普通 `.ts` 文件，不命名为 `.test.ts`      |
| 测试所需的最小静态输入                     | 沿用 `packages/battle/test/fixtures/`；小型输入优先就地定义，不复制完整内容包或原始资产库         |
| 考据、下载、费用报告、一次性调试与资源探测 | 实验临时目录或个人缓存，留在仓库外，不交付成正式测试                                              |

先查是否已有对应分组或机制测试，再决定新增文件。不要为精灵复刻在仓库根、`packs/base/src/`、`bin/__tests__/` 或 `packages/web-ui/` 散放测试。只有本次确实修改了 CLI、加载器或客户端行为时，才修改该模块的测试；单纯增加精灵不构成修改其他模块测试的理由。

新 V4 测试默认直接放在 `test/v4/` 下。当前 Vitest 和类型配置递归收集该目录，但 `lint:battle-v4` 的测试通配符为 `test/v4/*.ts`；不要随意新建子目录造成 lint 漏检。不要为单只精灵新建测试运行器、package script 或独立配置。

## 测试怎么写

- 使用 Vitest 和当前 V4 官方内容加载/战斗接口，从真实内容注册入口取得技能与效果。测试不能另写一份效果算法替代待测实现；先查看相近测试与 `base-metadata.ts`，只复用所需部分，避免整份复制大型辅助代码。
- 用例名称写清条件和结果，例如“有红心时强化两级并消耗一层”。按机制分组，必要时参数化成功/失败、无印记/有印记、首发/后备、不同形态；不要求每只精灵凑固定测试数量。
- 预期值来自已采用的资料与规则。断言具体伤害、回复、能力等级、印记消耗、持续/换场结果；只断言“造成了伤害”不能证明倍率、概率或副效果正确。
- 优先通过合法技能选择、回合推进和换场驱动真实行为。联动至少覆盖一条由队友实际技能产生印记的完整流程；局部边界测试可用现有公开战斗 API 准备状态，不能用手工状态注入取代全部联动验证。
- 固定 RNG seed；概率边界用受控随机输入覆盖触发与不触发，必要时单独覆盖未命中。替换随机函数或 spy 要局限于本测试实例并清理，不修改全局随机数或生产概率来让断言通过。
- 战斗、监听器、计时器、异步任务和 mock 沿用测试生命周期清理；不要吞掉待断言流程中的异常，也不要用任意 sleep 等待结算，优先等待明确的回合/消息事件。
- 只对新增或变化的机制补有价值的测试。复用效果、纯元数据补齐通常用既有验证及代表场景即可，不为每个 YAML 字段机械复制断言。禁止固定全包内容总数、源码文本匹配或为追随实现而改预期掩盖错误。
- 测试夹具必须符合实际接口合同。涉及 npm 工作区时，package.json、锁文件根记录与安装依赖元数据应一致；不要以简化夹具为由放宽生产校验。

## 验证与交付

从仓库根目录运行，分组名替换为实际文件名：

```sh
pnpm --filter @arcadia-eternity/data-pack-base build
pnpm test:battle-v4 <group>.test.ts
pnpm typecheck:battle-v4
pnpm lint:battle-v4
```

改动共享效果或引擎行为时再运行相关回归或完整 V4 套件。依赖声明过期按 AGENTS.md 刷新构建后重查。默认不运行 Web UI、浏览器或 Playwright；需要时由用户明确指定。

根 lint 和提交钩子可能忽略 V4 测试文件，不能据其成功宣称专用 lint 通过。交付前确认新增测试被现有配置收集，报告实际执行的文件、命令、通过/失败/跳过与未测项；临时日志、截图、调试脚本和整套实验副本不进入提交。

报告严格区分数据断言、直接触发某钩子和完整战斗场景。没有强制 MISS 用例时，不声称已实测未命中边界；免疫状态和属性免疫分别验证，添加印记尝试不等于成功。
