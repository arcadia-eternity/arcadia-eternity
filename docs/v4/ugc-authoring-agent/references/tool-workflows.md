# Author tool workflows

Start with `arcadia-content workspace <directory> describe` or MCP `workspace_describe`. Use the returned SDK API, capabilities and source revision. Opening or inspecting a project does not import its effect code.

The CLI emits JSON. `query`, `read`, `write` and `save` take JSON on stdin:

```sh
printf '%s' '{"file":"data/skills/strike.yaml"}' | arcadia-content workspace . read
arcadia-content workspace . check
arcadia-content workspace . test --execute
arcadia-content workspace . demo --execute
arcadia-content workspace . pack --execute
```

For file writes, pass `file`, `expectedVersion` and `text`; null version expects a new file. Prefer the coding assistant's normal file editing tools for TypeScript. The workspace watches the same directory, so changes become visible in the game. A failed version check means re-read the source and reconsider the change; do not retry a stale overwrite. Unsaved game forms remain in memory across object navigation. External changes require explicit field reconciliation followed by a separate save; the author can also discard drafts.

For structured edits, query content rows or `kind: locales` with `detail: full` first, then use MCP `content_apply` or CLI `save` with `{ changes: [...] }`. Each change includes `kind: record | locale | create-record`, `file`, `expectedVersion` and the complete `record` value. `create-record` uses a new file under the corresponding data directory, a new ID and `expectedVersion: null`; it never overwrites an existing file. New locale files also use null, and may refer to an object created in the same batch. Definition changes retain their `index` (null for a single-object file); locale changes use the content `id`. Preserve unknown fields. `sharedFields` describes read-only YAML anchors, aliases and inherited values; do not detach them to bypass the guard. Edit shared definitions through an intentional external source change. Inspect `complete` and each file in `results`: same-file edits are grouped, but multiple files do not commit as one transaction. On partial success, retain uncommitted work and re-read before retrying.

MCP configuration launches the installed `arcadia-content-mcp` executable with the explicit project directory. `--execute` enables tests, demonstration battles and packaging for a trusted local project; `--read-only` hides writes and tasks that generate files, including checks. The official base package is always read-only in author sessions, even without the flag. Its legacy `pack.json` source layout is indexed directly. Desktop installed-package browsing uses `--published`: this forces read-only access and follows the package manifest’s built content/presentation artifacts, including embedded locales, instead of assuming editable source files are shipped. Inspect capabilities before proposing edits. The default transport is stdio. No external server or model account is required.

Use discovered tool names. Core tools include `workspace_describe`, `workspace_context`, `content_query`, `source_read`, `source_apply`, `content_apply`, `check_start`, `job_get` and `job_cancel`. Execution-enabled sessions also expose `test_start`, `preview_start` and `package_build`. Start returns a job ID. Discover retained jobs with `job_list`; `job_get` returns compact state, diagnostics and candidate metadata, with optional `waitMs` up to 10000. Logs are omitted by default: read `job_output` chunks, reuse `nextCursor`, inspect `hasMore` and `truncated`. Query until a terminal state. `stale: true` is an old-source result, not proof the current files pass. Cancel stops the task, not source edits.

Standalone MCP and desktop both operate on the same disk files. The desktop connection configuration supplies `--context-file` for live `workspace_context` reads; this optional file is outside the project under Electron userData. It refreshes on navigation/form changes and every 30 seconds, is removed when the workspace closes, and expires after 90 seconds without a refresh. The reader verifies the bound project root. Without this option, `workspace_context` reports `not-configured`. Source reads still return disk files. Live context identifies unsaved drafts but does not lock the project: MCP writes update disk, and the desktop preserves dirty drafts and their original base versions for explicit reconciliation. File versions remain authoritative. Cooperating desktop, CLI and MCP saves serialize version checks and writes within each project; arbitrary external editors do not participate. Multi-file saves are not transactional. Partial `content_apply` results carry `isError` and per-file results, so retain uncommitted changes.

Desktop projects default to the Electron userData `ugc/projects` directory; existing directories are opened in place. Use the returned root rather than guessing a platform path. Moving a project to another machine requires its SDK/dependencies there; source export does not bundle node_modules. Source project export and an npm content tgz have different purposes.

Build/check/test use the fixed author commands. A headless demo proves engine execution, not image/audio playback or interactive UI acceptance. npm publication and production deployment are separate tasks.

## Discovery, teams and isolated battle checks

`content_query` searches localized names and accepts exact `id`, `contentKind`, `locale`, `namespace`, `packageName` and `scope: project | dependencies | all`. Default summaries omit the full record. Request `detail: full` before editing; use `nextOffset` to continue. Locale pages contain individual objects, not whole files. Declared installed dependencies are read without executing effects and return read-only provenance. Their file paths are relative to those packages, not valid bound-project edit targets. Missing or ambiguous dependencies are diagnostics, not permission to guess a target.

Use `team_list`/`team_save`/`team_remove` and `environment_list`/`environment_save` for saved project data. Saves require `expectedVersion`; null creates a file. These operations never select a team/environment, overwrite local drafts, or mutate a running match. Desktop file-change notifications refresh clean views promptly without focus changes; dirty drafts retain their base and show external-change conflicts. Users explicitly reload or resolve drafts. Environment changes require preparing a new candidate before a new battle.

`author_reference` and `arcadia://authoring/<topic>` expose actual SDK schemas/examples. Topics are species, skills, marks, team, environment, descriptions and effects. Read schema stage notes: linked-runtime schema is not source syntax. `asset_inspect` takes a declared resource ID; `includeImage: true` can return a bounded local image directly. HTTP assets are not downloaded; audio/SWF are metadata only.

For behavioral verification, `battle_create` takes a live preview `jobId`, two saved `teamIds`, and a fixed `seed`. It creates an independent automation battle; the user's manual match remains untouched. `battle_read` returns its `sessionId`, `revision`, state and legal `selections`. Submit a returned selection with `battle_action` and `expectedRevision`; never retry a timed-out action without re-reading. `battle_events` reads bounded event pages. `battle_reset` and `battle_close` also require the observed revision. At most four automation battles exist per preview. An engine failure returns `failure` and `stateCurrent: false` with a usable revision for reset/close; cached state is not current proof. Create/reset snapshots the latest saved team files and records their versions while retaining the captured candidate rules; team-only edits do not require rebuilding. Existing battles retain their own team snapshots. These tools never read unsaved UI values.
