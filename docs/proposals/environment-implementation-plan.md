# 仓库、组队、数值与环境的复核及实施计划

2026-11-18 · 首版实施中。产品名称确定为“对战环境”。作者编辑环境声明，房间在创建时锁定已准备的环境版本。仓库每只精灵保存一套配法，多套并存对应多只。个人队伍按成员顺序保存具体仓库精灵的实例 ID，同一只可供多队引用。各阶段在本文件排期，详细语义见[仓库适配](environment-storage-adaptation.md)、[编辑器](environment-team-editor.md)、[机制与环境](environment-rule-composition.md)、[原作依据](environment-reference-research.md)。

已接入共享的声明校验、队伍准入、玩法版本计算与规则能力检查。宿主按引擎 API 主版本 `4`、效果 SDK API 主版本 `2` 比对显式要求。含基础规则集的默认环境引用 `base:classic`。独立内容包可使用兼容默认规则。各平台安装与恢复仍按下列场景分别验收。

## 环境系统的交付与验收

已有的项目产物、环境依赖编辑、保存并应用、服务器绑定和运行租约作为接入点。原提案列有已落地范围及仍需回归的行为，见[环境依赖与配置模型](content-environment-model.md)。本次新增的是玩法规则的声明、解析、对外提供及对局采用。下表给出各项完成条件。

### 环境声明与房间锁定的版本

| 阶段             | 实施职责与验收                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0–1 · 声明与准备 | 以现有环境文档为编辑入口，分别处理环境 ID、并发保存用的声明修订和已准备版本的玩法标识。内容包提供定义与默认值，规则集提供可复用的调整，声明只记录依赖、选择和本地例外。用“晶攻火 2 倍改为 1.5 倍”验收：编辑时只增加一格覆盖，准备后可查整张有效表及该格来源。改动规则即使没有更换包，也应生成不同的玩法标识。见[管理协议](../../packages/protocol/src/management.ts)。                                                                         |
| 3 · 绑定与建房   | 工作区提交声明、锁和准备结果，服务器绑定管理开放、匹配及执行策略。建房取得一次包含玩法标识和材料的租约，将其传给 Ready 校验、开局和战斗宿主。房间及保留的恢复点各自释放持有的材料。服务器发布的 P2P 从房间租约对应的服务器版本取得材料，私人约战由双方核对文件或 HTTPS 来源提供的材料。两者均按建房时的玩法标识校验。见[环境租约](../../packages/server/src/runtime/environments.ts)及[房间入口](../../packages/server/src/runtime/rooms.ts)。 |
| 3–4 · 预览与执行 | 编辑器查询选中版本的目录、候选和规则；个人队伍继续引用仓库实例。向房间提交时展开队伍，由宿主按房间持有的版本复核，引擎使用该版本完成计算和结算。以相同队伍、相同随机输入验证管理页预览、房间摘要、实战相克倍率及快照恢复。                                                                                                                                                                                                                     |

**跨版本验收。** 先以 2 倍版本建甲房，留在等待阶段，再修改同一环境声明。分别模拟单格冲突导致准备失败、准备成功但服务器加载失败及重试成功。前两种情况下，甲房和该绑定下的新房均使用上次可用版本。重试成功后建乙房，两房显示同一环境名、不同玩法版本。向两房提交同一队伍，甲房从 Ready 到实战仍取 2，乙房取 1.5。甲房重连、换房主、同房再战和快照恢复均须复现原值。在 P2P 移走原材料后尝试用同名新版恢复，应提示需要原版本；补齐匹配材料后才可继续。详见[总设计的职责划分](environment-system-design.md#2-谁拥有什么)。

**绑定加载失败时的实施约定。** 服务器一次取得准备材料、环境名称和规则，整份加载通过后再切换绑定。工作区已成功应用 B、同一执行策略的服务器仍只能提供 A 时，管理端将绑定标为降级并记录失败原因，大厅和新建房间继续取得 A。没有可用旧版，或管理员改了执行策略时，绑定暂不可用。重试成功后，新房取得 B，已在等待的房间继续使用自己的版本。[绑定加载与重试用例](../../packages/server/test/managementBindings.test.ts)

### 现有性格和战斗属性迁入基础包

两项迁移共用一次内容格式与宿主能力升级。基础环境先完成现有数据的等价迁移，新增二代性格的资格及原作数据按阶段 5 单独验收。

| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0 · 固定旧值     | 从现有定义取出 25 种普通性格的六项倍率、23 种属性和 529 个有方向的相克倍率。保留独立的旧值对照，记录旧版队伍、内容包与固定随机种子的实战样本。水攻火为 2，火攻水为 0.5，另覆盖免疫和小数倍率。见[性格常量](../../packages/const/src/nature.ts)和[属性常量](../../packages/const/src/element.ts)。                                                                                                                                                                                                     |
| 1 · 发布与准备   | 扩展包清单、构建、加载、静态校验与已准备的目录，基础包发布普通性格、属性、官方相克表及展示引用。旧格式无新类别时按旧版基础资料解释。新格式解析带来源的稳定 ID，校验重复定义、性格六项修正、技能与物种的属性引用。从锁定包目录收集属性自带关系，检查每格归属与跨包条件。按攻防方向依次合成基础表、包自带关系、选用的规则集与环境覆盖，校验冲突并记录来源。把有效目录随环境提供给远端玩家。验证基础包从源码构建到已发布产物后能独立装配。见[当前基础包清单](../../packs/base/pack.json)。               |

## 跨系统复核

| 冲突或缺口                                                                               | 处理决定与检验办法                                                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 原方案同时依赖「移动后唯一位置」「复制队伍完全独立」。引入共享后，直接改表单会污染其他队 | 个人库以单次事务提交配法及成员关系。两队引用同一只精灵，在甲队选择“复制一只给本队”后换招，乙队仍引用原只。从仓库改原配法会影响仍使用它的队伍。用同一例子检验保存、取消、撤销和并发                                                                                                               |
| 仓库、作者项目、对战提交使用的队伍形状不同                                               | 个人库负责展开引用，作者项目和分享文件自含成员选择。共享编辑器操作临时候选，宿主接受固定版本的完整选择。测试换一台没有原仓库的机器仍能导入并试战                                                                                                                                                 |
| 个人档案还有独立校验和异步落盘路径                                                       | 本地档案 v1 内嵌队伍、限制六只，另有版本检查。网页桥接还投影旧 library 字段。升级外层版本及全部读写者，持久化成功才显示已保存。检查重启、旧版读新档、备份恢复和写入冲突。见 [schema.ts](../../packages/local-profile/src/schema.ts)、[profile.ts](../../packages/web-ui/src/services/profile.ts) |
| 仓库配法共享后，一队可在不同环境有不同结果，且队伍修订可能没有变化                       | 预览追踪成员修订及环境身份。环境偏好用于定位，实际使用绑定不可变版本。材料失效时保留草稿。已入房间的副本与本地编辑独立                                                                                                                                                                           |

## 阶段 3–4 补充验收：固定房间与临时环境

1. 阶段 3 用同名不同版本的个人环境测试房主更新请求。按已定的房间规则，跨版本更新请求被拒，房间锁定的版本和 Ready 状态保持原状。重连或转移房主后可重新提供相同版本并重新准备；不同版本另建房间。同步调整 privateRoom store、环境选择控件和现有个人房间替换测试。用同一支个人队伍先后进入两个同版本房间，覆盖甲房未提交改招、乙房进入后收到甲房迟到回执，以及重连后原房号被新房复用。只有原房实例及有效席位能恢复本场候选，个人仓库和乙房队伍应保持原值。
2. 阶段 4 让一份合法配法依次进入两个兼容环境，队伍成员引用及仓库记录数保持不变。准备同物种、同昵称但不同实例的两只精灵，切环境后按差异或短码区分，替换前检查整队。两队共用其中一只时分别执行“复制一只给本队”和“修改原精灵”，核对显示的队名、实际受影响队伍、仓库计数及已提交房间副本。
3. 在临时 P2P 环境保存含专属技能的配法，退出并释放临时材料，重启、导出、导入后仍保留选择。分别验证来源不可用、目标缺技能、目标有技能但禁用、相同版本恢复后的准入。只将临时改动用于本场时，个人配法保持进入前的值。
4. 大厅在版本 A 检查通过一支队伍。另存同名声明并准备 B，仅修改一条禁令，包与媒体保持相同。绑定加载 B 前，大厅和新房仍使用 A；加载后，用原队新建房间，以建房回执为准，B 禁用的技能须在房间编辑器定位，A 的通过结果不能用于 Ready。此前已建的 A 房重连仍允许该技能。
5. 服务器发布的 P2P 房间让两位参战者分别准备材料，客人取得完整锁定版后可先 Ready，房主只有公开目录或误取同名新版时仍无法开局。房主补齐原版并在开局请求中提交确认后，由玩家宿主复验双方队伍。用私人分享来源重复同一用例，断开来源再重连时保留草稿和房间版本，重新提供匹配文件后恢复准备。

**验收算例。** 最大体力固定为 600，冻气喷射用超额部分加威力，社区冰爆用超额部分加伤害。基础组值 500 时两招各加 100；方案组值 576 时各加 24；仅将社区冰爆固定为 550 时，冻气喷射加 24、冰爆加 50。补测 575／576／577，冻气喷射额外威力应为 0／0／1。此场景以独立的物攻门槛作为未入组对照。

**标签交叉验收。** 另用测试印记给己方一个专用战斗标签施加 +10。仅社区冰爆的 baseline 显式带此标签，官方冻气喷射与它同组。此时冰爆在自己的环境基准 550 上读到 560，额外伤害 40；己方冻气喷射仍加 24，对手无印记的冰爆仍加 50。保存并恢复后结果相同，移除印记后己方冰爆回到加 50。这一用例同时检验固定例外只固定环境初值、组成员资格不会自动生成战斗标签，以及标签的来源清理不会撤销环境方案。576 为实验候选，平衡值另由对照样本确定。

## 发布与回退

阶段 2 只对隔离样本启用新版写入。阶段 4 验证网页、桌面、CLI、恢复入口及编辑器后，才向用户开放档案迁移和新版写入。档案迁移前后保留版本识别和备份恢复路径。环境定义分版本发布，回退绑定只影响后续使用。恢复旧程序时保留新档，使用可被旧版读取的备份恢复工作。

复核证据按改动归属记录。档案与导出用 local-profile 和 CLI 往返样本，规则解析用 content-dev 测试，战斗数值与快照用 battle 测试，房间重验用 server 测试，组队使用网页端与安装后的桌面端走同一操作。下列场景是实施后的验收要求。正式开放 120 前，至少完成一次“测试配法保存 → 重启 → 导出恢复 → 基础拒绝 → 测试环境准入 → 战斗快照恢复”的完整验证。
